# Уведомления и права на задачи

У каждого участника собственная лента в рамках компании. Событие сохраняется в одной транзакции с изменением задачи или роли:

- Назначение задачи: уведомляются новые исполнители. Обычная правка текста без изменения исполнителей не создаёт событие. Один человек в нескольких отделах получает одно событие за операцию назначения.
- Изменение роли: уведомляется участник с изменённой ролью. При замене руководителя уведомления получают и новый руководитель, и прежний, переведённый в администраторы.
- При назначении приглашённому пользователю событие создаётся после принятия приглашения (или добавления существующего аккаунта в отдел). До этого действует обычное письмо с приглашением.

## API

Все методы требуют JWT и текущего доступа к компании:

- `GET /api/workspace/:workspaceId/notifications?cursor=...` — 20 собственных событий, `unreadCount` и `nextCursor`.
- `PATCH /api/workspace/:workspaceId/notifications/:id/read` — отметить своё событие прочитанным.
- `PATCH /api/workspace/:workspaceId/notifications/read-all` — отметить свои текущие события прочитанными.

Чужое событие нельзя прочитать, отметить или использовать как курсор. Ссылки на задачи учитывают текущие права. После удаления задачи историческое событие остаётся без ссылки. Клиент обновляет ленту раз в 30 секунд и при возвращении в окно.

## Почта

Оба типа событий также отправляются на email участника через существующий `MailService`. Используются `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `MAIL_FROM`, `APP_URL` и существующий `REDIS_URL`.

Очередь BullMQ `notification-emails` проверяет сохранённые события каждые 15 секунд. В Redis передаётся только ID события. Письмо отправляется после фиксации транзакции; сбой SMTP не отменяет задачу или смену роли. При перезапуске API или восстановлении Redis необработанные события снова попадают в очередь из PostgreSQL.

Предусмотрено 6 попыток с увеличением задержки от 30 секунд. Состояния `notifications.email_status`: `PENDING`, `SENT` (SMTP принял письмо), `SKIPPED` (назначение отменено, задача удалена или доступ отозван), `FAILED` (попытки исчерпаны). Без настроенного SMTP события остаются `PENDING`. Прочтение в интерфейсе не отменяет письмо.

После устранения причины окончательного сбоя оператор может вернуть нужные записи `FAILED` в `PENDING` и удалить соответствующие failed jobs из `notification-emails` по ID уведомления. Повторные задания для `SENT` не отправляют письмо заново. Используется стабильный Message-ID; при аварии между принятием письма SMTP и сохранением отметки в БД повтор возможен — SMTP не гарантирует доставку ровно один раз.

HTML письма экранирует пользовательский текст; также присутствует текстовая версия. Ключи и ответы SMTP не записываются в задания или сообщения об ошибках.

## Иерархия назначения

При создании или изменении списка исполнителей задача сохраняет автора назначения и его роль на тот момент: собственник → руководитель → администратор. Нижестоящий не может редактировать или удалять такую задачу; равный или вышестоящий может. Обычная правка текста не меняет автора назначения.

Общие задачи нескольких департаментов по-прежнему изменяет только собственник. Права на смену статуса не меняются: сотрудник меняет статусы кроме «Готово», администратор/руководитель/собственник могут завершить задачу.

У старых задач нет достоверной истории назначения, поэтому прежние права сохраняются до изменения исполнителей. Автор задним числом не назначается.

## Применение

Применить миграции `20260924110000_notifications` и `20260924120000_notification_emails`, выполнить `prisma generate` и обычную сборку/перезапуск API. Контейнеры, CI/CD и зависимости не менялись.
