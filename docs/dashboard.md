# Дашборд

`GET /api/workspace/:workspaceId/dashboard?departmentId=...`, авторизация Bearer JWT.

Без departmentId собственник получает всю компанию; остальные — свой первый департамент. Явно указанный отдел проверяется по текущему членству. Собственник переключается между всеми отделами, руководитель и администратор получают AI-сводку только своего отдела, сотрудник — только назначенные ему задачи и своё участие, без AI-анализа. Права проверяются при каждом запросе, сохранённая сводка не даёт дополнительных прав.

Задачи: активные — все статусы кроме done; просроченные — незавершённые со сроком раньше текущего дня; выполненные — done за всё время. Список показывает три ближайших по сроку активных задачи, включая просроченные. Общая задача считается один раз по ID в сводке компании. Команда — уникальные участники департаментов, принявшие приглашение, без собственника; руководители (CHIEF) входят в это общее число. Человек в нескольких отделах учитывается один раз. В личном обзоре сотрудника считаются только его задачи и участие.

## AI-сводка

Один запрос GigaChat рассчитывает риски, рекомендацию и оценку прогресса цели. Используется общий GigachatService: существующие OAuth, сертификаты, таймауты и повторы. Ответ проходит проверку структуры, диапазона процента 0–100, длины текстов и списка рисков. Процент — оценка AI, а не измерение бизнес-результата. Если нет цели или задач недели, вместо процента возвращается null; модель также может вернуть null при недостатке данных.

Неделя — семь календарных дней, включая текущий день, по Москве. В выборку входят задачи, созданные, изменённые или запланированные на этот интервал. Недельные показатели используют текущее состояние этих задач; отдельной истории изменения статусов пока нет. Контекст включает цель и приоритеты из брифа, текущие активные/просроченные задачи, точные счётчики всех задач недели и до 80 описаний с ближайшими сроками. Длинные описания ограничиваются, для задачи передаются до пяти исполнителей без email, а также до 50 примеров сводок отделов. Ограниченные выборки явно обозначены как примеры. Связи общей задачи с чужими отделами не передаются в анализ отдельного департамента.

Результат хранится в dashboard_snapshots отдельно для компании и каждого департамента. Первый запрос собственника или управляющего регистрирует сводку и ставит расчёт в Redis-очередь BullMQ. Следующий расчёт — отложенное задание через 24 часа после успешного ответа. Задания выполняет worker внутри API; открытая страница не нужна. При перезапуске API срок сохраняется в Redis и PostgreSQL, не начинается заново. Неактивные компании пропускаются. Процессного setInterval и ежеминутного опроса БД нет.

Каждый переход задачи из другого статуса в done запрашивает немедленный пересчёт компании и всех департаментов задачи, даже если предыдущая сводка ещё свежая. Повторное сохранение done ничего не запускает. Запросы записываются в той же транзакции, что и статус, и передаются в очередь после commit. При старте API и восстановлении соединения Redis очередь восстанавливает запросы из БД. Несколько быстрых завершений могут объединиться в расчёт по актуальному состоянию; изменение revision не позволяет старому ответу перезаписать более новый запрос.

ID заданий и атомарный захват записи в PostgreSQL предотвращают двойные расчёты при одновременных запросах и нескольких экземплярах API. Зависший захват можно повторить после полного таймаута GigaChat плюс одна минута; результат сохраняется только владельцем актуального захвата и версии запроса. При ошибке остаётся предыдущая сводка, очередь планирует повтор через 15 минут. Если API аварийно завершился после отправки запроса модели, при восстановлении возможен повтор внешнего запроса; в БД устаревший ответ не сохраняется. Ошибка первой генерации не подменяется нулевыми рисками или выдуманным процентом. В API состояния ready/updating/stale/unavailable/restricted и даты расчёта/периода.

Клиент обновляет текущие показатели раз в минуту и при возвращении на страницу, во время расчёта — раз в пять секунд. Повторный GET не пересчитывает свежую AI-сводку. Встречи и операционный журнал на этом этапе остаются пустыми, счётчики встреч — нули. Кнопки имитации принятия рекомендации убраны; автоматическое создание задач не реализуется.

## Обновление

Установить зависимости через `npm ci`, применить миграции (`npx prisma migrate deploy`), выполнить `npx prisma generate` и собрать API. Для первоначального дашборда нужна миграция `20260921100000_dashboard_snapshots`, для очереди — `20260921170000_dashboard_queue` (поле revision). Существующие задачи и роли не меняются. Контракт клиента сохранён, эта правка не требует обновления фронта.

Добавлена зависимость bullmq; используются прежние REDIS_URL и GIGACHAT_* переменные. Redis очереди и авторизации общий, соединение worker отдельное для блокирующих команд. Новых env-переменных и контейнеров нет, Docker/CI не менялись. Для очередей Redis должен сохранять данные и использовать maxmemory-policy=noeviction; расписание также восстанавливается из PostgreSQL при старте/переподключении. [Требования BullMQ к Redis](https://docs.bullmq.io/guide/going-to-production).

Описание формата запроса: [GigaChat — генерация ответа](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/post-chat).
