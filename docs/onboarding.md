# Авторизация, онбординг и диагностика

## Запуск

Нужны Node.js, PostgreSQL и Redis. Скопируйте `.env.example` в `.env`, укажите `DATABASE_URL`, `REDIS_URL` и собственный `JWT_SECRET`.

```sh
npm ci --ignore-scripts
npx prisma generate
npx prisma migrate deploy
npm run start:dev
```

API по умолчанию слушает порт 3001. Swagger: `/swagger`. Для запуска только на компьютере задайте `HOST=127.0.0.1`.

```sh
npm test
npm run lint
npm run build
npm run start:prod
```

Production запускается из `dist/src/main.js`. Миграции применяются отдельно перед запуском новой версии. В production задайте `NODE_ENV=production` и SMTP: фиксированный код `111111` действует только при `NODE_ENV=development`.

## Порядок запросов

1. `POST /auth/check-email` отправляет код; `success` означает, что пользователь уже существует.
2. `POST /auth/verify-code` проверяет email и код до ввода пароля, не расходуя код.
3. `POST /auth/login` или `/auth/register` повторно проверяет код и возвращает JWT. Код расходуется после успешного входа/регистрации. `GET /auth/me` проверяет текущий вход.
4. `POST /workspace/onboarding/company` создаёт или продолжает незавершённый черновик и возвращает его `id`.
5. `PATCH /workspace/:id/onboarding/company`, `/owner`, `/goals` сохраняют соответствующий шаг. Переход дальше возможен после успешного ответа. Последний шаг выставляет `onboardingComplete`.
6. `GET /workspace/status` и `GET /workspace/:id` позволяют продолжить незавершённую настройку. Статические маршруты объявлены до `/:id`.
7. `GET /workspace/diagnostics/questions` возвращает актуальные вопросы и варианты.
8. `POST /workspace/diagnostics/complete` принимает `{ workspaceId, answers }` и возвращает workspace с `diagnosticsAnalysis: { score, risks, summary }`.

Старый `/workspace/onboarding/complete` сохранён для совместимости и возвращает рабочее пространство. Оба маршрута `/complete` сохраняют поле `success: true` из прежнего ответа. Изменять онбординг и проходить диагностику может владелец. Одновременное создание черновика сериализуется; повтор успешной диагностики возвращает сохранённый результат и не сдвигает начало trial. Диагностику старого workspace с `diagnosticsComplete=true`, но без сохранённого JSON, можно повторить: прежняя дата trial сохраняется.

Ошибки кода и пароля учитываются атомарно в Redis, без потери попыток при одновременных запросах. Срок жизни кода сохраняется; истёкший или заменённый код не восстанавливается при обновлении счётчика.

## GigaChat

Заполните серверные `GIGACHAT_CREDENTIALS`, `GIGACHAT_SCOPE` и `GIGACHAT_MODEL`. URL авторизации и API вынесены в `.env.example`. Ключ не должен попадать во frontend или переменные `VITE_*`.

Модель должна быть доступна в ответе `/v1/models` для вашего аккаунта; в примере используется `GigaChat-2`. Для сертификатов GigaChat задайте `NODE_EXTRA_CA_CERTS` с путём к доверенному PEM-файлу до запуска Node.js. Если корневой сертификат уже установлен в ОС, на поддерживающих этот флаг версиях Node.js можно запускать `node --use-system-ca dist/src/main.js`. Проверку TLS отключать не требуется.

Интеграция получает OAuth-токен, кеширует его до истечения срока и обновляет один раз при 401. Неизвестные вопросы и неверные индексы вариантов не попадают в запрос модели. Повторяющиеся вопросы и отсутствие содержательных ответов отклоняются. Текст вопросов и выбранных вариантов берётся из серверного справочника.

JSON модели проверяется до сохранения: допустимы только корректные типы и завершённый ответ с `finish_reason=stop`. Пустой массив рисков допустим, если модель не выявила рисков по ответам; он не вызывает повторную генерацию. После первой попытки выполняется до пяти повторов при временных ошибках, сетевых сбоях и неверном формате. По умолчанию запрос ограничен 20 секундами, весь анализ — 120 секундами. 402/403 не повторяются; `Retry-After` учитывается в пределах общего времени.

Ответы сохраняются до анализа. Если все попытки неудачны, API возвращает 503 с кодом `GIGACHAT_UNAVAILABLE`: результат и trial не создаются, ответы остаются доступными для повторного запроса. Параллельный анализ одного workspace возвращает 409.

Для тестов используются подменённые HTTP-ответы; настоящие ответы и доступность модели нужно отдельно проверить с рабочим ключом. Проверка TLS остаётся включённой.
