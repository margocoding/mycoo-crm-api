# Партнёрская программа

Партнёром становится любой зарегистрированный пользователь MyCoo. Подтверждение email и вход используют существующие `/auth/*`; `POST /partners/register` создаёт профиль без модерации и без требования активной подписки. Кабинет доступен и при истёкшей подписке. Данные прототипа из браузера не импортируются в финансовый учёт.

## Запуск

1. Установить зависимости из lockfile: `npm ci`.
2. Применить аддитивные миграции: `npx prisma migrate deploy`.
3. Собрать приложение: `npm run build`.
4. Один раз задать на сервере `PARTNER_ADMIN_LOGIN` и `PARTNER_ADMIN_PASSWORD`, затем выполнить `npm run partner:admin`. Команда создаёт только первого администратора и не меняет существующие учётные записи. После выполнения убрать эти две переменные из окружения. Стандартного пароля нет.
5. Запустить приложение прежней командой. Во фронте использовать прежний `VITE_API_URL`, указывающий на API с префиксом `/api`.

Нужны существующие PostgreSQL, Redis, `JWT_SECRET` и SMTP для подтверждения email. Dockerfile и CI не менялись. Административные сессии живут 12 часов; смена логина/пароля в `/admin/settings` требует текущий пароль и отзывает все старые сессии. В БД хранятся хеши паролей и токенов, а не их исходные значения.

## Условия и привязка клиента

Начальные, ранее демонстрационные условия: 20% от учитываемой оплаты, первые 12 календарных месяцев после регистрации клиента, 14 дней ожидания, минимум вывода 5 000 ₽. Перед публикацией администратор должен установить утверждённые условия в настройках. Изменение создаёт новую версию, применяется к последующим оплатам и не переписывает прошлые комиссии или возвраты.

Ссылка `/?partner=CODE` сохраняется в текущей вкладке до регистрации, максимум на 30 дней. Учитывается первая действующая партнёрская ссылка. При регистрации фронт передаёт `partnerCode`; сервер связывает нового пользователя с партнёром в той же транзакции. Существующих клиентов задним числом не привязываем; самоприглашение не учитывается. Личная реферальная скидка `?ref=` работает отдельно по прежним правилам.

В таблице клиент представлен названием первой созданной им компании и отдельным идентификатором реферала. Email, идентификатор аккаунта и данные задач клиента партнёру не передаются. Оплата привязана к аккаунту плательщика: это соответствует существующей модели подписок MyCoo.

## Оплаты, возвраты и выплаты

`BillingService.confirmVerifiedPayment()` вызывается существующей интеграцией Robokassa после проверки подписи и суммы. Продление подписки и партнёрское начисление происходят в одной транзакции. Повторный callback не добавляет новую комиссию. До подтверждения оплаты комиссии нет; отменённый неоплаченный заказ не влияет на баланс.

По умолчанию сохраняется тестовый режим платёжки: `ROBO_KASSA_TEST_MODE=true`. Для реальных оплат нужно явно установить `false` и настроить рабочие `ROBO_KASSA_PASSWORD1`/`ROBO_KASSA_PASSWORD2` из кабинета Robokassa. Режим записывается в заказ при создании; изменение настройки не превращает старый тестовый заказ в рабочий. Все ранее существовавшие заказы миграция помечает тестовыми, поскольку прежний код всегда передавал `IsTest=1`. Тестовые оплаты не создают партнёрских начислений и не увеличивают доступный к выводу баланс. [Правила тестового режима Robokassa](https://docs.robokassa.ru/ru/testing-mode).

При начислении сохраняются оплата, версия условий, сумма комиссии и дата доступности. Денежные значения в БД — целые копейки; API отдаёт рубли. После даты доступности комиссия автоматически участвует в доступном балансе при чтении и операциях, отдельный таймер не требуется.

Календарные даты ручной оплаты и фиксации выплаты (`YYYY-MM-DD`) используются по московскому времени, UTC+3. Время события внутри выбранного дня не может быть раньше регистрации клиента или создания заявки. Полные ISO-временные метки учитываются как точные моменты времени.

Заявка на выплату проверяет реквизиты, минимальную сумму и доступный баланс, резервирует деньги и сохраняет снимок реквизитов. Статусы: `new`, `review`, `approved`, `paid`, `rejected`. Для отказа обязательна причина. Фиксация выплаты возможна после одобрения; сумма и дата записываются в историю. При частичной выплате остаток резерва освобождается. Перед одобрением и выплатой баланс проверяется повторно.

Ручная сверка в админке позволяет учесть пропущенную оплату, возврат или отдельную корректировку с причиной. ID оплаты уникален. Возврат отменяет комиссию пропорционально фактически возвращённой сумме по исходной ставке. Несколько частичных возвратов в сумме точно отменяют исходную комиссию. Возврат после выплаты образует задолженность и уменьшает доступные средства.

Этот модуль **не переводит деньги в банк и не инициирует возврат в Robokassa**. Администратор фиксирует уже выполненные выплаты/возвраты. Для будущего автоматического возвратного webhook нужно сначала проверить подпись провайдера и вызывать учёт возврата со стабильным идентификатором операции. Публичного endpoint, принимающего утверждение клиента об оплате, нет.

Комиссии, корректировки, возвраты, параметры операций, история статусов и версии условий защищены от `UPDATE`/`DELETE` триггерами PostgreSQL. Исправление финансовой записи выполняется новой корректировкой. Повтор финансового запроса с тем же `idempotencyKey` возвращает первоначальный результат; тот же ключ с иным содержимым отклоняется. Конкурирующие заявки и возвраты сериализуются.

## API

События новых заявок, одобрения, отказа и оплаты создают личное уведомление и email-outbox в той же транзакции. Уведомления доступны в `/partner/account/notifications` без компании и подписки. Существующие события до миграции не рассылаются задним числом. Для отправки используется прежняя SMTP-конфигурация и очередь `partner-notification-emails` в Redis; при недоступности SMTP записи сохраняются в БД и повторяются с увеличением задержки до часа. Перезапуск или потеря очереди не теряют ожидающие письма. Событие уникально, повтор операции не создаёт новое уведомление. DB-lease исключает параллельную отправку; SMTP Message-ID постоянный. Как у любой SMTP-доставки, при аварии между приёмом письма сервером и сохранением результата возможна повторная попытка с тем же Message-ID.

Полный журнал партнёра доступен в `/partner/account/ledger` с курсорной пагинацией по 20 записей, включая корректировки без привязки к клиенту. В админке у заявки доступна история статусов с автором, временем и причиной; у финансовых записей отображается автор операции.

- `GET /partners/terms` — публичные текущие условия.
- `GET /partners/me/ledger?cursor=...`, `GET /partners/me/notifications?cursor=...` — собственные страницы журнала и уведомлений; курсор другого партнёра отклоняется.
- `POST /partners/me/notifications/:id/read`, `POST /partners/me/notifications/read-all` — отметить свои уведомления прочитанными.
- `GET /partner-admin/payouts/:id/history` — история заявки, только администратор.
- `GET /partners/me`, `POST /partners/register`, `PUT /partners/me/details`, `POST /partners/me/payouts` — JWT пользователя, только собственные данные.
- `/partner-admin/login`, `/partner-admin/session`, `/partner-admin/logout`, `/partner-admin/credentials` — отдельная серверная авторизация администратора.
- `/partner-admin/data`, `/partner-admin/terms`, `/partner-admin/payouts/:id/review`, `/partner-admin/payouts/:id/pay`, `/partner-admin/adjustments`, `/partner-admin/payments`, `/partner-admin/payments/:id/refunds` — реестр и финансовые операции, только с административной сессией.

Все пути относительно `/api`; типы тел запросов описаны в `src/partners/partner.dto.ts`. Для операций вывода, фиксации выплаты, корректировки, ручной оплаты и возврата обязателен `idempotencyKey`. API кабинета возвращает согласованный снимок данных из транзакции; финансовые решения принимает сервер.

## Проверки

- `npm test`, `npm run lint`, `npm run build`.
- `npm run test:partners` после сборки и применения миграций к отдельной локальной тестовой БД. По умолчанию: PostgreSQL `127.0.0.1:5548/mycoo_partner_test`, Redis `127.0.0.1:6388/1`. Можно задать `DATABASE_URL` и `REDIS_URL`; скрипт отказывается работать с удалённой или не тестовой БД.

Интеграционные проверки создают пользователей с адресами `example.test`, используют локальный код подтверждения и тестовые подписи платёжных уведомлений. Писем и внешних платежей не отправляют. Проверяются изоляция кабинетов, подпись платежа, повтор callback, конкурентные заявки, возвраты, реквизиты, неизменяемость журнала и отзыв сессий.
