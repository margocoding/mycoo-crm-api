# Диагностика записи встречи

22 октября 2026 на mycoo.io первоначально повторён сбой: обычный Chrome устанавливает WebRTC-соединение и передаёт синтетические аудио- и видеодорожки, но запись остаётся в `starting` с ошибкой. Интерфейс до исправления ошибочно сообщал «Идёт запись».

После получения SSH установлены причины: Egress требовал 4 CPU на сервере с 2 vCPU, бакет MinIO `calls` отсутствовал, ссылки на файл указывали на внутренний адрес Docker. Настройка Egress под одну запись, создание приватного бакета и отдельный публичный endpoint подписанных ссылок устранили эти сбои. Код текущей ветки установлен на сервере отдельным локальным образом. Повторная проверка встречи `cmvjl8tmy00092gnzyapuhfch` прошла: MP4 143,545669 с / 12 582 344 байта, H.264 + AAC, воспроизведение в Chrome, SpeechKit и черновик протокола с двумя задачами. Проверялся один тестовый аккаунт с синтетической речью; взаимный разговор двух разных пользователей остаётся отдельной проверкой.

## Что исправлено

- `starting` сохраняется, пока LiveKit Egress не вернёт `ACTIVE` (1). Ответ `STARTING` (0) больше не выдаётся за начавшуюся запись.
- После получения ID Egress обработчик опрашивает существующую операцию, не отправляя повторный запуск.
- Успешный опрос сбрасывает старую ошибку и задержку повторных попыток. Запрос остановки, поступивший во время запуска, сохраняется.
- Ошибка содержит этап: запуск, проверка состояния, остановка/сохранение или распознавание. В журнале есть ID встречи, записи, операции, номер попытки и HTTP-статус calls.
- Сырые ответы провайдеров, адреса с параметрами, пароли и токены не пишутся в новые диагностические события. Для известных ошибок конфигурации сохраняется только классификация.

Эти изменения исправляют состояние и диагностику. Исправления конфигурации сервера необходимы отдельно: один только этот патч не создаёт бакет и не меняет ресурсы Egress. Полный журнал изменений и порядок следующего деплоя сохранены на сервере в `/opt/my_coo/RECORDING-FIX-20261022.md`. API и calls временно используют локальные исправленные образы с `pull_policy: never`; после слияния патчей следует вернуть проверенные registry-образы согласно журналу.

## Проверка сервера

Тест 22.10.2026: запуск записи в **10:35:04 UTC / 13:35:04 МСК**, завершение встречи около **10:38:37 UTC**. Meeting ID: `cmvjel92t00032gnz9hmrgpb9`; recording ID: `cmvjemxdo00052gnzngho84eh`.

На сервере сначала проверить имена контейнеров, затем получить журналы нужного интервала:

```sh
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
docker logs --since '2026-10-22T10:33:00Z' --until '2026-10-22T10:40:00Z' --timestamps mycoo-crm-api-1
docker logs --since '2026-10-22T10:33:00Z' --until '2026-10-22T10:40:00Z' --timestamps mycoo-crm-calls_microservice-1
docker logs --since '2026-10-22T10:33:00Z' --until '2026-10-22T10:40:00Z' --timestamps livekit-server
docker logs --since '2026-10-22T10:33:00Z' --until '2026-10-22T10:40:00Z' --timestamps livekit-egress
```

Имена выше взяты из предыдущего развёртывания и должны быть сверены с `docker ps`. Не пересылать `.env`, полный `docker inspect` или ключи; в существующих журналах скрыть секреты перед передачей.

После установки исправления искать `calls_request_failed` и `meeting_recording_failed`. `authentication` означает отказ HTTP 401/403 между API и calls; `storage` — известный ответ об отсутствии параметров S3 в calls; `livekit` — известный ответ об отсутствии параметров LiveKit; `timeout` — истечение времени запроса. `response` с HTTP-статусом требует журнала calls/Egress. Это направления диагностики, а не установленная причина текущего сбоя.

Полная приёмка после исправления конфигурации: два разных участника в обычных браузерах, взаимный звук и видео, запуск записи, переход в `recording`, остановка, доступный MP4, распознанная речь из этого MP4, черновик протокола. Проверка SDK или отдельного аудиофайла не заменяет этот сценарий.

## Проверки кода

`npm test`, `npm run lint`, `npm run build`. Добавлены регрессии для STARTING/ACTIVE, повторного опроса, восстановления после ошибки, одновременной остановки, отказа Egress и сохранения файла. Диагностический клиент проверяется на отсутствие секретов в журнале.

## Публикация изменений

В текущей основной ветке Backend CD реагирует на завершение Backend CI без фильтра события и результата; даже проверка PR может запустить `docker compose pull` и `docker compose up -d` на сервере. Перед открытием PR безопасно ограничить развёртывание успешной проверкой push в `main` либо согласовать это поведение с владельцем сервера. Публикация отдельной ветки сама по себе Backend CI/CD не запускает.
